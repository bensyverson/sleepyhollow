# SleepyHollow — vision

*2026-08-20 · Ben Syverson & Claude · status: agreed direction*

**SleepyHollow is a headless WebKit browser designed for agents.** It renders
real pages with the system's WebKit engine and exposes everything an agent
needs — pixels, structure, semantics, behaviour — through a small CLI whose
input is verbs and whose output is structured text. One binary; no bundled
browser, no profile, and — until you *name* something — no state, no socket,
no background process. Nothing hangs: every operation either answers or
becomes an exit code with a reason.

## Why

Every headless browser an agent can use today is a GUI application with the
head cut off. Chromium's headless mode drags along a profile directory, a
keychain integration, first-run flows, a crash reporter, a GPU pipeline and a
~200 MB bundled binary — and its automation story, the Chrome DevTools
Protocol, is a *debugger* protocol: stateful WebSocket sessions, event
subscriptions, numeric object handles. It was designed so that humans could
build DevTools GUIs, and every agent framework on top of it (Puppeteer,
Playwright, chromedp) is a thick client working around that mismatch.

Agents don't work that way. An agent composes tools the way a shell does:
run a verb, read structured output, branch on an exit code. The measure of an
agent tool is not how much it can do in one process but how little an agent
has to hold in its head to use it correctly — and how impossible it is to
misuse. The prior art for this repo is `job`: a bare command that serves as a
primer, subcommands that teach themselves, errors that say what to do
instead.

The need is not hypothetical. A production project (we'll call it Starlight)
drives its browser tests through Chrome with no protocol at all — an
injecting same-origin middleware (an earlier iteration used a reverse
proxy), `--dump-dom`, and JSON parsed out of a `<pre>` tag — because that
was *less* machinery than CDP. That harness carries standing workarounds for
Chrome not exiting after `--dump-dom`, modal macOS keychain prompts, and a
headful first-run window that once popped eleven sign-in dialogs at a human.
And its automation covers exactly one engine — Chrome; Firefox is checked by
hand — which is how two Safari-only bugs shipped in a single day: **WebKit —
the engine on every Mac and iPhone — is the engine agent tooling can't
currently see.**

Apple ships WebKit as a system framework. A tool that links `WebKit.framework`
is a few hundred kilobytes, launches in tens of milliseconds, inherits
security updates from the OS, and *is* the third engine. That is the
opportunity: not a smaller Chromium, but the browser that would exist if the
requirements had been an agent's from day one.

## Philosophy — agent-first, in five rules

1. **stdout is the API.** Verbs in, structured output out (`--out <file>` to
   write it elsewhere), exit codes that mean something. Each verb's default
   output is its tersest faithful form — HTML for `dom`, an indented outline
   for `ax`, JSON where the data is inherently structured — and a stable
   JSON shape is always one `--format json` away. Output never depends on
   the environment: the same invocation emits the same bytes in a pipe and
   in a terminal. No daemon an agent must babysit, no socket protocol, no
   client library required to participate.
2. **Everything terminates.** Every operation carries a default timeout. A
   tool that can hang is a tool an agent cannot be trusted with; "no answer"
   must always become an exit code and a reason.
3. **Ephemeral by default, state by name.** A bare invocation leaves no
   trace: non-persistent data store, no profile, no keychain, no caches that
   outlive the process. Persistent things exist only when named, and naming
   one *is* creating it — no ceremony. There are two kinds: **sessions** (a
   live page that outlives one invocation) and **jars** (cookies that
   outlive a session). Anything named is listable and prunable.
4. **The page has more than one true form.** Pixels, DOM, computed style, the
   accessibility tree, the wire log — each is a first-class read, because an
   agent should query the cheapest representation that answers its question,
   not screenshot-and-squint.
5. **Deterministic by construction.** Waiting is a primitive of the tool, not
   a polling loop in the agent. Dialogs never block: `alert`/`confirm`/
   `prompt` are auto-answered by policy and recorded. Fixed window size,
   named theme, no ambient state — the same invocation renders the same page.

## The grammar

Every page verb has one shape:

```
sleepy <verb> <url | --session <name>> [verb-args] [--format …]
```

- **A URL means an ephemeral load** — a fresh page that vanishes when the
  process exits. Loading options (`--wait-for`, `--inject`, `--theme`,
  `--size`, `--jar`, dialog flags) apply whenever a URL is given.
- **`--session <name>` means a live page** owned by a named session; the
  verb runs against its current state.
- **Verb classes.** *Loading/read verbs* (`load`, `shot`, `pdf`, `archive`,
  `dom`, `query`, `style`, `ax`, `find`, `wire`, `eval`) take either page
  source. *Act verbs* (`click`, `fill`, `submit`) require `--session` —
  acting on a page that evaporates at exit is write-only. *Management verbs*
  (`sessions`, `jars`) take neither.
- **One-shot flows compose by flags.** Loading verbs accept ordered,
  repeatable action flags executed after the load event and before the
  read — `sleepy shot <url> --fill '#q=webkit' --click '#go' --wait-for
  '.results'` — so a two-step check never forces naming a session.

  > **Correction (2026-08-20, ruled during wave 2).** This bullet
  > originally said the steps run "after the load settles", which
  > contradicted the example on the next line: waiting for `.results`
  > only makes sense *after* the click that produces them. The ruling is
  > the example's reading: each step **auto-waits** for its own selector
  > (within the load's single budget) before acting, and `--wait-for` is
  > the final gate after all steps, immediately before the read. A step
  > whose selector never becomes actionable is a timeout (exit 3), not a
  > clean negative — it waited, honestly, and ran out of budget. The
  > session act verbs (`click`/`fill`/`submit`) keep immediate
  > no-match-is-negative semantics for now; see `project/backlog.md`.

An agent that has learned one verb has learned the shape of all of them.

> **Amendment (2026-08-20, ruled during wave 1):** verb-specific arguments
> are named flags (`--selector`, `--property`, `--text`), never second
> positionals. The page source owns the bare-argument slot, and
> ArgumentParser silently misassigns a verb's positional to it when
> `--session` replaces the URL — a trap the dom family hit in practice.
> `shot --element` set the precedent; the read bullets below reflect it.

## Goals

- The best way for an agent to *see* and *verify* a web page on a Mac.
- A genuine WebKit engine for cross-engine testing — the coverage Chromium
  and Gecko harnesses structurally cannot provide.
- Light enough to run per-test: system framework, instant launch, dozens of
  concurrent sessions without ceremony.
- A CLI an agent can learn entirely from the tool itself, `job`-style.
- A small, focused open-source tool other projects adopt for the same reasons.

## Non-goals

- **Not a crawler, not a scraper framework.** No queueing, no politeness
  policies, no distributed anything. One page at a time, driven by something
  smarter than it.
- **Not cross-platform.** Explicitly Apple-only, and unapologetic about
  reaching for macOS frameworks where they help (Vision OCR, PDFKit,
  NSAppearance). WPE WebKit is the acknowledged portability story if a Linux
  need ever becomes real; designing for it now would forfeit the advantage.
- **Not a mocking proxy.** Wire-level *observation* is in; request rewriting,
  response stubbing and traffic interception are out for now — they change
  the tool from a witness into a participant, and the participant business is
  deep. The wire recorder's mechanism (a fetch wrapper; see §6) would make
  stubbing cheap — Starlight's recorder stubs refusals this way — so staying
  out is a choice, held until a concrete consumer needs it.
- **Not a spec-complete WebDriver.** No W3C WebDriver conformance, no
  Selenium compatibility. Those serve a different master.
- **No virtual time.** WebKit exposes none publicly. Timer-heavy pages are
  handled honestly (real waits) or by injected script (a timer-accelerator
  user script), never by forking WebKit. Starlight's virtual-time clock is
  also the cautionary tale: its jumps made "sleep two seconds" resume the
  instant response headers arrived, reporting a state that never existed.

## What — required for 1.0

Each feature names the need it serves and how it fits an agent-first
workflow. The feature *is* the verb; discoverability is part of the spec.
Everything in this section ships in 1.0; deferred work lives in Post-1.0
below.

### 1. Load & capture

- **`sleepy load <url>`** — the base verb: load, settle, report the facts
  (final URL, HTTP status, console-error count) with a meaning-bearing exit
  code. *Need:* the smoke test — "does this page even load?" — deserves a
  verb with no further apparatus. With `--session` it navigates an open
  session to a new URL. Every other loading verb is `load` plus a read.
- **`sleepy shot <url>`** — render at a given `--size`, write a PNG.
  *Need:* the baseline act of seeing. *Agent fit:* one verb replaces the
  Chrome recipe (two keychain flags, fresh profile dir, `--headless=new`,
  background-and-poll) that currently lives in a gotchas file.
- **`--element <selector>`** — screenshot one element's rect
  (`WKSnapshotConfiguration(rect:)`). *Need:* the thing under test is rarely
  the whole page; a movers-button bug hid 2,400 px down a page because
  captures were viewport-shaped, and two byte-identical "before/after" shots
  both missed the element. *Agent fit:* small images are cheap to attach,
  cheap to diff, and unambiguous about what changed.
- **`--full-page`** — capture the entire scroll height, not the viewport.
- **`--theme light|dark`** — render under either appearance
  (`NSAppearance` on the web view). *Need:* theme-aware pages break in the
  mode nobody screenshotted. *Agent fit:* two invocations, two facts, no
  system-settings mutation.
- **`sleepy pdf <url>`** — paginated PDF (`WKWebView.createPDF`).
  *Need:* print stylesheets and paginated artifacts (reports, invoices) are
  rendering targets too. *Agent fit:* a PDF is a reviewable, attachable
  deliverable.
- **`sleepy archive <url>`** — `.webarchive` of page + subresources
  (`createWebArchive`). *Need:* evidence. A bug report that carries the page
  *as it was* — assets included — outlives the server state that produced it.

### 2. Read — the page's many forms

- **`sleepy dom <url|--session>`** — serialized DOM to stdout, as HTML (its
  native form); `--format json` for a tree. *Need:* the Starlight harness's
  entire browser contract is "give me the final DOM"; today that's
  `--dump-dom` plus entity-unescaping workarounds.
- **`sleepy query --selector <sel>`** — matched elements as JSON: text, attributes,
  geometry, visibility. *Need:* "is there exactly one identity control on
  this page?" should not require parsing HTML in an agent's head.
  *Agent fit:* selector in, facts out, `--count`/`--exists` variants carry
  the assertion in the exit code.
- **`sleepy style --selector <sel> [props…]`** — computed styles. *Need:* today's CSS
  bugs ("did the reset apply?", "what painted this background?") are settled
  by screenshot forensics; the computed value is the actual fact.
- **`sleepy ax <url|--session>`** — **the accessibility tree.** Default
  output is an indented text outline — `button "Publish" (disabled)` — the
  cheapest faithful read of the page's semantics; `--format json` for the
  full tree. *Need:* the a11y tree is the page as assistive tech reads it —
  roles, names, states, structure, with presentation stripped away.
  *Agent fit:* this is the semantic diff of what an agent usually wants:
  "is there a button named Publish, and is it disabled?" answered in one
  query without selectors, plus every WCAG name/role audit for free. No
  mainstream headless CLI leads with this; it is the flagship read.
- **`sleepy find --text <text>`** — the engine's own text search (`WKWebView.find`).
  *Need:* "does the rendered page actually say it?" — independent of DOM
  shape, matching what a user would find with ⌘F.

### 3. Act

- **`sleepy eval --js <js>`** — evaluate JS (`callAsyncJavaScript`): `await`
  supported, arguments passed as JSON (`--args '{"n": 3}'`), result returned
  as JSON, page errors as structured failures. *Need:* the universal escape
  hatch; the Starlight scenarios are, in the end, JS that computes marks.
  *Agent fit:* an eval that returns `{"marks": …}` with exit 0/1 *is* a test
  — a result of exactly `false` exits 1, the same clean negative `find` uses.

  > **Corrected in place (2026-08-20, act & eval leaf):** this bullet read
  > `sleepy eval <js>`, a second positional the flag-grammar amendment above
  > forbids. The script is `--js`, and the exit-1-on-`false` contract is
  > stated rather than left to the reader.
- **Isolated world by default** (`WKContentWorld`). *Need:* the tool's
  instrumentation must not collide with page JS — Starlight's harness shares
  the page world and simply hopes; hope is not a contract. `--page-world`
  opts into the shared world when the page's own state is the subject.
- **`sleepy click / fill / submit`** — convenience verbs over event dispatch,
  against a `--session`; the same actions ride loading verbs as ordered
  flags for one-shot flows (see The grammar). *Need:* the three moves that
  make up almost every flow, without the agent hand-writing dispatch
  boilerplate. Honest about mechanism: synthesized events, not OS-level
  hit-testing.
- **Dialog policy: decline everything, record everything.** By default
  `alert` is acknowledged, `confirm` cancelled, `prompt` cancelled,
  `beforeunload` allowed to leave — declining is the least-side-effect
  answer (an auto-accepted "Delete this item?" is an agent-caused incident).
  Every dialog lands in the output, so the agent sees what was declined and
  reruns with `--confirm=accept` / `--prompt-text=…` deliberately. Never
  blocking (`WKUIDelegate`). *Need:* a modal is an agent-trap; the Chrome
  keychain-prompt saga is the cautionary tale.
- **`sleepy cookies get|set`** — read or write cookies
  (`WKHTTPCookieStore`), against a session's live store or a named jar.
- **Jars — named cookie state, independent of sessions.** `--jar <name>` on
  any loading verb (and on `open`) attaches a persistent jar; naming it
  creates it. A session without `--jar` holds cookies in memory only, and
  they die with it. **`sleepy jars list|clear|rm`** manage them. *Need:*
  authenticated flows — mint a login once, reuse it by name from any
  invocation, one-shot or session. The login survives a session's idle TTL
  because the state lives in the jar, not the helper.

### 4. Wait — determinism as a primitive

- **`--wait-for <selector | js-predicate | idle | load>`** on every loading
  verb, with `--budget <ms>` as the ceiling. *Need:* the difference between
  a flaky harness and a boring one is who owns the waiting. The Starlight
  harness's virtual-time trick exists because Chrome offered no "wait until
  the page says it's done"; `--wait-for '#cardjstest'` is that, directly.
  *Agent fit:* the agent states the condition; the tool owns the clock; a
  timeout is an exit code with the page's last state attached, not a hang.

### 5. Sessions — opt-in, named, listable

- **`sleepy open <url> --name <n>`** creates a persistent session — a small
  helper process owning the web view, keyed by name. If the name is already
  open, `open` **fails loudly**: naming is a claim, and silently reusing
  another flow's cookies, scripts and history is exactly the ambient state
  rule 5 forbids. The error teaches the two intents apart: "Session `login`
  already open (4m, at https://…) — `sleepy load --session login <url>` to
  navigate it, `sleepy close login` to replace it."
- **Every helper supervises itself.** There is no central daemon: each
  session self-terminates on an idle TTL, and `sleepy sessions
  list|prune|close` reap orphans lazily (dead process + stale socket ⇒
  removed). One wedged page can never take down the fleet, and when nothing
  is named, nothing is running.
  *Need:* multi-step flows — open, log in, navigate, assert, screenshot —
  across separate CLI invocations; this is half the reason the tool exists.
  *Agent fit:* naming is the opt-in to state (philosophy #3): a bare
  `sleepy shot` stays pure; anything named is discoverable (`list`),
  disposable (`prune`), and inspectable later. The `job` claim/TTL pattern,
  applied to pages.

### 6. Observe

- **Console & page errors**, captured via script-message handlers
  (`WKUserContentController`) and reported on stderr or `sleepy console`.
  *Need:* in Chrome-land this alone forces CDP; an agent debugging a page
  needs the page's own complaints.
- **`sleepy wire <url|--session>`** — the request log, in two layers, both
  public API. The **inventory**: every request's URL, type, timing, sizes
  and status, from `WKNavigationDelegate` (main-frame facts) plus
  `PerformanceResourceTiming` — no methods or bodies at this layer; that is
  a platform truth, stated up front.

  > **Correction (2026-08-20, wire spike):** the inventory promises more
  > than WebKit gives. `responseStatus` has never shipped in any Safari, so
  > the inventory can never show subresource HTTP status — status exists
  > only for the main frame (`WKNavigationDelegate`) and for whatever the
  > fetch log observes. Sizes need Safari ≥ 16.4 and are same-origin-only
  > (Timing-Allow-Origin does not unlock them). The inventory layer is:
  > URL, type, timing (TAO-gated cross-origin), sizes same-origin on
  > current WebKit. Details: `project/2026-08-20-wire-spike.md`. The **fetch log**: a document-start
  recorder wrapping `window.fetch`, reporting method, headers, request and
  response bodies, and status through a script message handler — structured
  messages, not Starlight's DOM-exfiltration-and-regex. The recorder
  normalizes through `new Request(input, init)`, closing the gap that makes
  Starlight's recorder silently drop fields when a page passes a `Headers`
  or `Request` object. Honest limits: the fetch wrapper must live in the
  page world (an isolated world cannot see the page's `fetch`), so page
  code can observe it; subresources appear in the inventory only.
  *Need:* "what did the page ask for, and what came back?" — Starlight's
  assertions ("one edit ⇒ exactly one POST, urlencoded, status 200, body
  contains the new value") are the acceptance test; its thesis — *counting
  requests is not reading the responses* — is the requirement. Rewriting
  stays a non-goal.
- **`--inject <file>`** — user scripts at document start/end
  (`WKUserScript`), as a flag on loading verbs and on `open` — a flag
  rather than a verb because user scripts must be installed before the
  load. *Need:* retires the injecting-middleware pattern entirely:
  instrumentation becomes a flag, not a rewriting layer the harness
  maintains.

### 7. The CLI itself — a feature, not a wrapper

- Built on **Apple's ArgumentParser** (the PixelPeeper pattern).
- **Bare `sleepy` is a primer**: what the tool is, the three most common
  invocations, where help lives — the `job` doctrine. `--help` per
  subcommand carries examples, not just flags.
- **Errors teach.** "No session named `login-flow` — `sleepy sessions list`
  shows two open sessions" beats a stack trace. Every failure states the
  next move.
- **`--format` everywhere.** Each verb defaults to its tersest faithful
  form and documents the alternatives (`json` always among them); `--out
  <file>` on anything that emits an artifact; exit codes documented per
  verb.

## Post-1.0

Planned, believed in, and deliberately not in 1.0.

- **`sleepy read`** — OCR the rendered pixels (Vision framework
  `VNRecognizeTextRequest`). *Need:* text living in `<canvas>`, images and
  charts is invisible to every DOM read; a Mac-native tool gets OCR for one
  import.
- **`sleepy shot --diff <baseline>`** — PixelPeeper as a library dependency;
  see PixelPeeper composition below for why the coupling waits.
- **The observatory: `sleepy serve`** — a local dashboard showing every live
  session as a tile in a grid: name, URL, age, and a periodically refreshed
  screenshot (the capture machinery sessions already have, pointed at a
  human). *Need:* concurrent sessions driven by agents are invisible by
  design — headless means nobody sees the work. *Agent fit, inverted:* this
  is the human-in-the-loop surface. An operator glances at the grid and
  knows what the fleet is doing, the same way a preview page makes a
  component reviewable. Ships as a local web page first (the library can
  already screenshot; serving a grid of PNGs is small); a native menu-bar
  app is a possible later skin over the same session API.
- **History verbs** (`back`, `forward`) — when a consumer wants history
  semantics tested, not before.
- **Custom-scheme handlers** (`WKURLSchemeHandler`) for serving local
  fixtures without a web server — likely cheap, deferred until a consumer
  asks.

## How — lightly

- **One SwiftPM package, two products** (the PixelPeeper pattern): the
  `SleepyHollow` library owning all behaviour, and a thin `sleepy`
  executable (`sleepyhollow` as the formal alias) that is ArgumentParser
  plus calls into the library. The library is the product other Swift tools
  import; the CLI is its first consumer.
- **WKWebView without a window**: instantiated headless with an explicit
  frame, `WKWebsiteDataStore.nonPersistent()` unless a jar or session names
  otherwise, run loop driven by the host process. Swift 6 concurrency
  throughout.
- **Sessions** are self-supervising helper processes owning one web view
  each, listening on a Unix socket under `~/.sleepyhollow/sessions/<name>/`;
  the CLI is a thin client to them. Jars persist under
  `~/.sleepyhollow/jars/<name>/`. One-shot verbs host the web view
  in-process and exit.
- **Testing**: the library is testable against local fixture pages served
  in-process; the CLI gets golden-output tests. The tool that exists to make
  other projects' browser tests honest must be embarrassingly well-tested
  itself.

## PixelPeeper composition

Two Swift packages by the same author invite a library-level marriage; the
agent-first lens says take it, but not first. **1.0 composes by chaining** —
`sleepy shot --element … --out a.png` then PixelPeeper compares — keeping
SleepyHollow dependency-free and each tool's job crisp. **Post-1.0 adds
`sleepy shot --diff <baseline>`**, with PixelPeeper as a library dependency:
a single verb whose *exit code is the visual regression verdict* is worth
the coupling, because it collapses screenshot-compare-decide into one
atomic, scriptable act. The doc records the order deliberately: chaining
proves the seam before the dependency lands.

## Open questions

- The idle TTL default for sessions (the reaping *mechanism* is settled:
  self-terminating helpers plus lazy cleanup in `sessions list|prune`).
- Whether `sleepy ax` reads via the JS accessibility computation, the AX
  API, or both (implementation spike; the verb's contract is stable either
  way).
- Wire-layer details to spike: which `PerformanceResourceTiming` fields
  (notably `responseStatus`) exist on the oldest supported WebKit, and the
  fetch recorder's response-body limits (opaque and streaming responses).
- License (MIT assumed for a small OSS tool) and minimum macOS version
  (whatever `callAsyncJavaScript` + `createPDF` require — macOS 12+).
